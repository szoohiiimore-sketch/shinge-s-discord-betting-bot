## 1. Source Authority Model

### 1.1 Domain Split

The two sources cover completely non-overlapping domains. There is no match, team, league, or sport that could appear in both APIs.

| Entity | Traditional Sports | Esports |
|--------|-------------------|---------|
| **Source** | The Odds API | PandaScore |
| **Schema `ApiSource`** | `THE_ODDS_API` | `PANDASCORE` |
| **Schema `SportCategory`** | `TRADITIONAL` | `ESPORTS` |

This partition is enforced at the schema level by the `Sport.externalApiSource` field. Every entity downstream of a Sport inherits its source authority implicitly through the `sportId` foreign key chain.

### 1.2 Source Responsibilities by Entity

| Entity | Owner API | Basis |
|--------|-----------|-------|
| **Sport** | The Odds API (traditional) / PandaScore (esports) | Each source defines its own sport domain |
| **League** | The Odds API (traditional) / PandaScore (esports) | Competition structures differ per domain |
| **Team** | The Odds API (traditional) / PandaScore (esports) | Derived from match opponents in both sources |
| **TeamLeague** | Same as League | Junction follows the League's source |
| **Match** | The Odds API (traditional) / PandaScore (esports) | Complete domain separation |
| **OddsSnapshot** | The Odds API only | PandaScore does not provide bookmaker odds |

### 1.3 Match Ownership

**Traditional sport matches are owned exclusively by The Odds API.**
**Esports matches are owned exclusively by PandaScore.**

A match's source is determined by its parent Sport record. No match can change source once created.

### 1.4 Team Ownership

Traditional sport teams are derived from The Odds API event payloads. Teams are not first-class objects in The Odds API — they appear as name strings on each event. Team records must be synthesized from this data.

Esports teams are first-class objects in PandaScore with stable numeric IDs, slugs, and full metadata. This makes esports team management structurally simpler than traditional.

### 1.5 League Ownership

Traditional leagues correspond to The Odds API's sport keys. Each sport key (e.g., `soccer_epl`) represents both a sport group and a specific competition. The mapping separates these into a Sport record (from the `group` field) and a League record (from the `key` and `title` fields).

Esports leagues correspond to PandaScore's `League` objects. A League in PandaScore is the organising body (e.g., ESL, Blast Premier). Tournaments are events within a League. For V1, the PandaScore `League` maps to the `League` schema entity.

### 1.6 The Odds Constraint for Esports

PandaScore provides match data but no bookmaker odds. The Odds API does not cover CS2, Valorant, or LoL. **Esports matches will have no `OddsSnapshot` records in V1.**

This has a direct consequence for the AI analysis pipeline: esports matches can be analysed for team form and head-to-head record, but value assessment (`valueAssessment`, `expectedValue`) requires odds and cannot be calculated without them. The analysis service must handle the no-odds case explicitly.

This is an architectural constraint for V1. It does not require schema changes — `Analysis.oddsUsed` is already nullable and `OddsSnapshot` has no mandatory relationship to `Analysis`.

## 2. Entity Identity Mapping

### 2.1 Overview

Each external API uses its own ID scheme. The schema provides two identity anchors per entity:

- An internal UUID primary key (`id`) — generated by PostgreSQL, invisible to external systems
- An external ID field (`externalId`, `externalSportKey`) — the stable, source-assigned identifier used to correlate API data to database records

The challenge is that The Odds API does not assign IDs to teams. All other IDs are stable and API-assigned.

### 2.2 Sport Identity

| | The Odds API | PandaScore |
|---|---|---|
| **Source field** | `sport.group` (e.g., `"Soccer"`) | `match.videogame.slug` (e.g., `"cs2"`) |
| **`Sport.slug`** | lowercase group: `"soccer"` | videogame slug: `"cs2"` |
| **`Sport.name`** | group display name: `"Soccer"` | videogame display name: `"CS:GO"` |
| **`Sport.externalSportKey`** | group slug: `"soccer"` | videogame slug: `"cs2"` |
| **`Sport.externalApiSource`** | `THE_ODDS_API` | `PANDASCORE` |
| **`Sport.category`** | `TRADITIONAL` | `ESPORTS` |

The `Sport.slug` must be globally unique. Since traditional sport groups and esports videogame slugs occupy different namespaces (no videogame is called "soccer"), collisions are not expected. If one were introduced in the future, prefixing with source (e.g., `"oa:soccer"`, `"ps:cs2"`) resolves it without schema changes.

**Important:** The Odds API returns multiple sport objects with the same `group` (e.g., `"soccer_epl"` and `"soccer_bundesliga"` both have `group: "Soccer"`). These must map to a single `Sport` record. The first encounter creates the Sport; subsequent encounters update it if the name changed.

### 2.3 League Identity

| | The Odds API | PandaScore |
|---|---|---|
| **Source field** | `sport.key` (e.g., `"soccer_epl"`) | `match.league.id` (e.g., `42`) |
| **`League.externalId`** | sport key: `"soccer_epl"` | league ID as string: `"42"` |
| **`League.name`** | sport title: `"English Premier League"` | league name: `"ESL"` |
| **`League.slug`** | sport key: `"soccer_epl"` | league slug: `"esl"` |
| **Unique key** | `(sportId, externalId)` | `(sportId, externalId)` |

The `League.slug` must be unique. For The Odds API, the sport key is already a slug. For PandaScore, use the league's native slug.

### 2.4 Team Identity

**PandaScore (simple):**

| Field | Value |
|-------|-------|
| **`Team.externalId`** | `match.opponents[n].opponent.id.toString()` (e.g., `"1234"`) |
| **`Team.name`** | `match.opponents[n].opponent.name` |
| **`Team.slug`** | `match.opponents[n].opponent.slug` |
| **Unique key** | `(sportId, externalId)` |

**The Odds API (derived):**

The Odds API does not assign team IDs. Teams appear as name strings on each event: `home_team: "Manchester United"`. A stable synthetic `externalId` must be derived from this string.

Derivation rule:

```
externalId = slugify(team_name)

Where slugify:
  1. Lowercase the entire string
  2. Trim leading and trailing whitespace
  3. Replace one or more non-alphanumeric characters with a single hyphen
  4. Remove leading or trailing hyphens

Example:
  "Manchester United" → "manchester-united"
  "Paris Saint-Germain" → "paris-saint-germain"
  "Brighton & Hove Albion" → "brighton-hove-albion"
```

The unique key `(sportId, externalId)` ensures that the same slugified name within the same sport produces the same Team record across all ingestion runs.

**Risk:** The Odds API occasionally uses alternate name forms for the same team (e.g., "Man City" vs "Manchester City"). If this occurs, two separate Team records will be created for the same real-world entity. In V1 (friends-only, known small sport set), this risk is acceptable. The Team table's `name` field can be updated on each upsert so the most recent spelling is always stored. Deduplication of alternate names is not in scope for V1.

### 2.5 Match Identity

Both APIs assign IDs to matches, but in different formats.

| | The Odds API | PandaScore |
|---|---|---|
| **Source field** | `event.id` (UUID string, e.g., `"a1b2c3..."`) | `match.id` (integer, e.g., `98765`) |
| **`Match.externalId`** | Prefixed: `"oa:{event.id}"` | Prefixed: `"ps:{match.id}"` |
| **Unique key** | `externalId` (globally unique) |  |

**Namespacing is required.** The Odds API uses UUIDs and PandaScore uses integers. While UUIDs and integers are unlikely to collide as strings, explicit namespacing (`oa:` and `ps:`) makes the source of every match record unambiguous and prevents any future collision if a third source is added.

### 2.6 TeamLeague Identity

`TeamLeague` is a junction table derived from match data. When a team participates in a match for a given league, a `TeamLeague` record is created if it does not already exist.

The unique key `(teamId, leagueId)` handles deduplication. This record has no source-specific identity field — it is purely derived.

## 3. Deduplication Strategy

### 3.1 Principle: Idempotent Upserts

Every entity write must be idempotent. Running the same ingestion job twice must produce the same database state as running it once. This property enables:

- Safe BullMQ retries on failure
- Safe re-ingestion after bugs or outages
- No need for compensation transactions

### 3.2 Upsert Patterns by Entity

**Sport:**
- Lookup by `slug` (unique)
- On match: update `name`, `status` if changed
- On miss: create

**League:**
- Lookup by `(sportId, externalId)` (unique composite)
- On match: update `name`, `slug`, `status` if changed
- On miss: create (requires Sport to already exist)

**Team:**
- Lookup by `(sportId, externalId)` (unique composite)
- On match: update `name`, `slug` if changed
- On miss: create (requires Sport to already exist)

**TeamLeague:**
- Lookup by `(teamId, leagueId)` (unique composite)
- On match: no-op (status remains ACTIVE)
- On miss: create (requires both Team and League to already exist)

**Match:**
- Lookup by `externalId` (globally unique)
- On match: update `status`, `homeScore`, `awayScore`, `result`, `lastFetchedAt`
- On miss: create (requires Sport, League, homeTeam, awayTeam to already exist)
- **Never change** `sportId`, `leagueId`, `homeTeamId`, `awayTeamId`, `startTime` after creation

**OddsSnapshot:**
- Always INSERT — never update or delete
- No deduplication applied
- `capturedAt` is set to the current timestamp at insert time
- The analysis layer retrieves the most recent snapshot per `(matchId, bookmaker, market, outcome)` using `capturedAt` ordering

### 3.3 Dependency Order Within a Single Job

For every ingestion run, entities must be written in dependency order within a single transaction or sequential batch:

```
Sport → League → Team → Match → TeamLeague → OddsSnapshot
```

A match cannot be written before its league and teams exist. A TeamLeague record cannot be written before the team and league it joins exist.

**Recommended approach:** Within a single job execution, perform writes in this order:

1. Upsert Sport
2. Upsert League (requires Sport)
3. Upsert both Teams (requires Sport)
4. Upsert Match (requires Sport, League, both Teams)
5. Upsert TeamLeague × 2 (requires Team, League)
6. Insert OddsSnapshots (requires Match)

If any step fails, BullMQ retries the whole job. Because all writes are idempotent, partially completed writes are safe to re-run.

### 3.4 Matches With Missing Opponents

PandaScore's `match.opponents` can be `null` or contain fewer than two entries (e.g., TBD teams in bracket stages). Such matches cannot be persisted because `homeTeamId` and `awayTeamId` are non-nullable.

**Rule:** Skip any match where `opponents` is null or does not contain exactly two entries of type `Team`. Log the skip at debug level. Do not treat as an error.

## 4. Synchronization Strategy

### 4.1 Time Windows

Every ingestion run operates on a defined time window, not the entire historical dataset.

| Job Type | Window | Rationale |
|----------|--------|-----------|
| **Match discovery** | Now + 7 days forward | Captures upcoming matches for analysis preparation |
| **Live match updates** | Now − 3 hours → Now + 3 hours | Catches matches that started recently or are running |
| **Odds updates** | Matches with startTime within 48 hours | Prioritise near-term matches where odds are most actionable |
| **Result sync** | Matches with startTime within past 48 hours and status not FINISHED | Catch recently completed matches for settlement |

### 4.2 Traditional Sports Synchronization (The Odds API)

**Sports and Leagues:** Fetched by calling `GET /v4/sports` (one API request). Sports and leagues are relatively static — new leagues are added infrequently. Sync on application startup and on a daily basis thereafter.

**Matches and Odds:** The Odds API `/sports/{key}/odds` endpoint returns both match data (commence time, team names) and bookmaker odds in a single response. This means match ingestion and initial odds ingestion happen in the same API call, maximising information per quota unit.

**Two-tier polling:**
- Tier 1 (every 30 min): Fetch `/odds` for each monitored sport. Write all matches in the 7-day window. Write OddsSnapshots with `isMain` set on the primary bookmaker. This is the match discovery and baseline odds cycle.
- Tier 2 (every 15 min): For matches with `startTime` within the next 48 hours, fetch `/odds` with the specific `eventIds` filter. Write new OddsSnapshots. This is the high-frequency line-movement capture cycle.

**Quota management:** The Odds API charges per request based on event count. The quota remaining is tracked in the `OddsApiClient.getQuotaState()` method. Before each ingestion run, the job must check the remaining quota. If quota is below a minimum threshold, skip the run and log a warning. The threshold is configurable in `BettingConfig` or a dedicated ingestion config section.

### 4.3 Esports Synchronization (PandaScore)

PandaScore does not have a quota limit in the same billing model as The Odds API. Pagination must be handled (PandaScore returns pages of 50 results by default).

**Matches:** Use `getUpcomingMatches(videogame)` and `getRunningMatches(videogame)` for each configured videogame (`cs2`, `valorant`, `lol`). Collect all pages before writing.

**Teams:** Teams are embedded in match payloads (`match.opponents[n].opponent`). Extract and upsert teams as part of match ingestion. No separate team-fetch call is needed for match-level team data. The `getTeam(teamId)` endpoint is available for enrichment if needed in a future sprint.

**Match results:** PandaScore includes results in the match payload itself (`match.results`, `match.winner`). A match with `status: "finished"` already contains final scores. No separate result-fetch call is needed.

**Polling:** Every 30 minutes for match discovery. No second-tier odds poll (no odds available). For live match tracking, `getRunningMatches` is called on the same 30-minute cycle.

### 4.4 Status Mapping

API statuses must be mapped to the schema's `MatchStatus` enum at ingestion time.

**The Odds API** does not return match status in the `/odds` response. Status is inferred:
- If `commence_time` is in the future → `SCHEDULED`
- If `commence_time` is in the past and the match has bookmaker odds → likely `LIVE` (but The Odds API does not confirm this reliably)
- The Odds API does not report `FINISHED`, `CANCELLED`, or `POSTPONED` via the odds endpoint

This is a structural limitation: **traditional match status cannot be determined from The Odds API alone.** In V1, traditional matches remain `SCHEDULED` until a separate result source updates them. Settlement of traditional predictions requires either manual status updates or an additional data source. This constraint must be documented for the settlement sprint.

**PandaScore** provides explicit status:

| PandaScore Status | Schema `MatchStatus` |
|-------------------|----------------------|
| `not_started` | `SCHEDULED` |
| `running` | `LIVE` |
| `finished` | `FINISHED` |
| `canceled` | `CANCELLED` |
| `postponed` | `POSTPONED` |

**PandaScore Result Mapping** (`match.winner` + `match.draw`):

| Condition | Schema `MatchResult` |
|-----------|----------------------|
| `match.draw === true` | `DRAW` |
| `match.winner.id === homeTeam.externalId` | `HOME_WIN` |
| `match.winner.id === awayTeam.externalId` | `AWAY_WIN` |
| `match.winner` is null and `match.draw` is false | `null` (not yet settled) |

Scores for esports are game counts (best-of series). The `homeScore` and `awayScore` fields represent the number of maps/games won, not a traditional score.

## 5. BullMQ Queue Design

### 5.1 Queues Used for Ingestion

Only two of the existing queues are used in the ingestion sprint:

| Queue Name | `QueueName` Enum | Purpose in Ingestion |
|------------|-----------------|----------------------|
| `match-fetch` | `MATCH_FETCH` | Fetch and upsert Sport, League, Team, Match entities |
| `odds-fetch` | `ODDS_FETCH` | Fetch and insert OddsSnapshot records for near-term matches |

The other queues (`ai-analysis`, `prediction`, `settlement`, `alert`) are not touched in this sprint.

### 5.2 Job Types

**`match-fetch` queue job types:**

| Job Name | Trigger | Payload |
|----------|---------|---------|
| `sync-traditional-sport` | Repeatable (every 30 min) | `{ sportKey: string }` |
| `sync-esports-game` | Repeatable (every 30 min) | `{ videogame: VideogameKey }` |
| `sync-reference-data` | Repeatable (daily) | `{}` — triggers sports/leagues refresh |

**`odds-fetch` queue job types:**

| Job Name | Trigger | Payload |
|----------|---------|---------|
| `sync-odds-for-sport` | Enqueued by `sync-traditional-sport` on completion | `{ sportKey: string, matchExternalIds: string[] }` |

The `sync-traditional-sport` job enqueues a `sync-odds-for-sport` job after successfully persisting matches, passing the external IDs of matches within the 48-hour window. This creates a natural dependency chain without coupling the two workers directly.

### 5.3 Job Scheduling

Repeatable jobs are registered at application startup by the ingestion module. Each configured sport and videogame gets its own repeatable job.

**Traditional sports:** One `sync-traditional-sport` job per sport key. Each job is independent. Failure of one sport's job does not affect others.

**Esports games:** One `sync-esports-game` job per videogame key (`cs2`, `valorant`, `lol`). Each job is independent.

The sport and videogame lists to monitor are configuration values (not hardcoded), drawn from `BettingConfig` or a new `IngestionConfig` section. This allows adding or removing a sport without code changes.

### 5.4 Job Execution Flow

**`sync-traditional-sport` execution:**

```
1. Fetch /sports/{sportKey}/odds from The Odds API
   → Check quota before calling; skip if below threshold
2. For each event in the response:
   a. Upsert Sport (from event.sport_key group)
   b. Upsert League (from event.sport_key)
   c. Upsert homeTeam (from event.home_team)
   d. Upsert awayTeam (from event.away_team)
   e. Upsert Match (from event, using "oa:{event.id}" as externalId)
   f. Upsert TeamLeague × 2
3. Collect externalIds of matches with startTime within 48 hours
4. If any such matches exist, enqueue one sync-odds-for-sport job
5. Log: matches processed, new vs updated, odds jobs enqueued
```

**`sync-odds-for-sport` execution:**

```
1. Fetch /sports/{sportKey}/odds with eventIds filter
   → Check quota before calling
2. For each event in the response:
   a. Resolve Match by externalId ("oa:{event.id}")
   b. If match not found: log warning, skip (should not happen)
   c. For each bookmaker → market → outcome:
      - Insert OddsSnapshot with isMain=true for primary bookmaker,
        isMain=false for all others
      - isLive = (match.status === LIVE)
3. Log: matches processed, snapshots inserted
```

**`sync-esports-game` execution:**

```
1. Fetch upcoming matches for videogame (getUpcomingMatches)
2. Fetch running matches for videogame (getRunningMatches)
3. Collect all pages for both responses
4. For each match in combined results:
   a. Skip if opponents is null or length !== 2
   b. Skip if either opponent type is not "Team"
   c. Upsert Sport (from match.videogame)
   d. Upsert League (from match.league)
   e. Upsert homeTeam (from opponents[0])
   f. Upsert awayTeam (from opponents[1])
   g. Upsert Match (using "ps:{match.id}" as externalId)
      - Map status, scores, result from match payload
   h. Upsert TeamLeague × 2
5. Log: matches processed, new vs updated
```

**`sync-reference-data` execution:**

```
1. Fetch /sports from The Odds API
2. For each active sport:
   a. Upsert Sport
   b. Upsert League
3. Log: sports and leagues synced
```

### 5.5 Inter-Queue Communication

The `sync-traditional-sport` job enqueues `sync-odds-for-sport` jobs. This is the only inter-queue communication in the ingestion sprint. The odds job is enqueued with a short delay (e.g., 5 seconds) to allow the match writes to commit before the odds job attempts to look them up.

No other queues are triggered by ingestion jobs in this sprint.

### 5.6 Job Configuration

| Job Type | Attempts | Backoff | Timeout |
|----------|----------|---------|---------|
| `sync-traditional-sport` | 3 | Exponential, 30s initial | 120s |
| `sync-esports-game` | 3 | Exponential, 30s initial | 120s |
| `sync-reference-data` | 2 | Exponential, 60s initial | 60s |
| `sync-odds-for-sport` | 3 | Exponential, 30s initial | 60s |

Rate limit errors (`RateLimitError`) carry a `retryAfterMs` value in their context. The worker should honour this as the backoff delay when it is present rather than using the default exponential backoff.

## 6. Persistence Model

### 6.1 What Is Written

Every entity written during ingestion maps directly to a schema model. No intermediate or staging tables are used.

| Schema Model | Write Pattern | Frequency |
|---|---|---|
| `Sport` | Upsert by `slug` | Once at startup + daily refresh |
| `League` | Upsert by `(sportId, externalId)` | Once at startup + daily refresh |
| `Team` | Upsert by `(sportId, externalId)` | Every match-fetch run |
| `TeamLeague` | Upsert by `(teamId, leagueId)` | Every match-fetch run |
| `Match` | Upsert by `externalId` | Every match-fetch run (creates or updates) |
| `OddsSnapshot` | Insert only | Every odds-fetch run |

### 6.2 Match Update Rules

When a Match record already exists and a new ingestion run returns data for the same `externalId`, the following fields may be updated:

| Field | Update rule |
|-------|-------------|
| `status` | Always overwrite with the latest API value |
| `homeScore` | Overwrite if the new value is non-null |
| `awayScore` | Overwrite if the new value is non-null |
| `result` | Overwrite if the new value is non-null |
| `lastFetchedAt` | Always overwrite with current timestamp |

The following fields must **never change** after initial creation:

| Field | Reason |
|-------|--------|
| `externalId` | Immutable identity |
| `sportId` | Domain partition is permanent |
| `leagueId` | Competition membership is fixed |
| `homeTeamId` | Match opponents do not change |
| `awayTeamId` | Match opponents do not change |
| `startTime` | Scheduled kickoff is fixed (postponement creates a new entry in practice) |

### 6.3 OddsSnapshot Design

`OddsSnapshot` is an append-only time series. Each ingestion run adds new records; existing records are never modified or deleted.

**Primary bookmaker selection (`isMain` flag):** For each (matchId, market) combination, exactly one bookmaker per ingestion run should be marked `isMain=true`. The primary bookmaker is determined by a prioritised list in configuration (e.g., `["pinnacle", "betfair", "williamhill"]`). If none of the preferred bookmakers are present, the first bookmaker in the API response is used.

**Consumer pattern:** The analysis service retrieves the most recent snapshot per `(matchId, bookmaker, market, outcome)` ordered by `capturedAt` descending. The `@@index([matchId, capturedAt])` index in the schema supports this efficiently.

**Retention:** OddsSnapshot records for FINISHED, CANCELLED, or POSTPONED matches are not cleaned up in V1. Storage growth is acceptable at the scale of ≤5 users and a small number of monitored sports.

### 6.4 Per-Run Write Volume Estimate

For orientation only — actual numbers depend on active sports and match count.

| Event | Estimate |
|-------|----------|
| Traditional match-fetch (5 sports, 50 matches each) | ~250 match upserts, ~500 team upserts |
| Traditional odds-fetch (50 near-term matches, 5 bookmakers, H2H only) | ~500 OddsSnapshot inserts per run |
| Esports match-fetch (3 games, 30 matches each) | ~90 match upserts, ~180 team upserts |
| OddsSnapshots per day (odds-fetch every 15 min) | ~48,000 inserts at 500/run |

At this scale, Neon's free tier (10 GB storage) will not be exhausted within V1's operational lifetime.

## 7. What Must Never Be Persisted

### 7.1 Raw API Responses

Raw JSON payloads from either API must never be stored in the database. They are large, denormalised, and redundant with the normalised entity records. If debugging requires access to raw responses, log them at `debug` level during development only.

### 7.2 Bookmaker Metadata

The Odds API returns bookmaker objects with `key`, `title`, `region`, and `last_update`. Only `bookmaker.key` (the string identifier) is persisted in `OddsSnapshot.bookmaker`. The `title`, `region`, and `last_update` fields are discarded.

### 7.3 Player Data

PandaScore's `Team` objects include a `players` array with full player profiles. Players are not in the V1 schema and must not be persisted. Discard the `players` field entirely during team extraction.

### 7.4 Game-Level Data

PandaScore's `Match` object includes a `games` array representing individual maps or rounds within a series. These sub-game records are not in the schema and must not be stored. The top-level match results (series score) are sufficient for V1.

### 7.5 API Quota and Rate Limit State

The `OddsApiClient.getQuotaState()` method returns quota remaining. This state is held in-memory by the client instance and must not be written to the database. If the application restarts, the quota state is refreshed from the next API response header. Redis ephemeral storage for quota state is acceptable if needed across restarts, but PostgreSQL persistence is not.

### 7.6 Intermediate Processing State

No staging table, job-local state table, or processing log table should be created. BullMQ's own job state (pending, active, failed, completed) is the canonical record of processing history. No shadow tracking in PostgreSQL.

### 7.7 Historical Odds

The `OddsSnapshot` model captures odds at the time of ingestion. The Odds API's historical odds endpoint (`GET /v4/sports/{sport}/odds-history`) must not be called in V1. Historical odds backfilling is expensive in quota terms and irrelevant for real-time recommendation generation.

### 7.8 Tournament Series Metadata

PandaScore's `Serie` type represents groupings above the tournament level (e.g., "Season 2024"). These are not in the V1 schema and must not be persisted.

### 7.9 Odds for Terminal Matches

OddsSnapshot records must not be created for matches with status `FINISHED`, `CANCELLED`, or `POSTPONED`. If an odds-fetch job receives data for a match in a terminal state, the odds records must be discarded.

## 8. Failure Recovery Strategy

### 8.1 Idempotency as the Primary Defence

Because every entity write is an upsert (or a pure INSERT for OddsSnapshot, which has no uniqueness requirement), the primary recovery strategy is simply: **retry the entire job from the beginning**. No partial state cleanup is required.

BullMQ's built-in retry mechanism with exponential backoff handles transient failures automatically. The `retryable` flag on application errors is already correctly set:

| Error Type | `retryable` | BullMQ action |
|---|---|---|
| `ExternalApiError` (5xx) | `true` | Retry with backoff |
| `RateLimitError` | `true` | Retry after `retryAfterMs` delay |
| `AuthenticationError` | `false` | Move to failed queue immediately |
| `DatabaseError` (connection) | `true` | Retry with backoff |
| `DatabaseError` (constraint) | `false` | Move to failed queue |

### 8.2 Quota Exhaustion

If The Odds API quota is exhausted:

1. The API returns HTTP 429 with a `Retry-After` header
2. The client throws `RateLimitError` with `retryAfterMs` in context
3. The BullMQ worker honours the retry delay
4. All subsequent jobs for the same API queue up behind the delay
5. When quota resets (monthly), jobs resume automatically

If quota is running low (below a configurable threshold, e.g., 10% remaining):
- Log a warning on every ingestion run
- Do not reduce polling frequency automatically in V1 (manual intervention expected for a friends-only bot)

### 8.3 PandaScore Pagination Failures

If a paginated response fails mid-collection (e.g., page 3 of 5 fails):

1. The job throws before any writes occur
2. BullMQ retries the entire job
3. All pages are re-fetched from page 1 on retry
4. Since writes are idempotent, pages 1 and 2 can safely be re-processed

### 8.4 Partial Dependency Failure

If a job successfully writes some entities but fails before writing others (e.g., upserted 40 of 50 matches before a database connection error):

1. BullMQ retries the entire job
2. The first 40 upserts are no-ops on retry (idempotent)
3. The remaining 10 are written on the retry run
4. No data loss, no duplicates

### 8.5 Persistent Failures

If a job exhausts all retry attempts and moves to BullMQ's failed queue:

1. The failed job is retained in Redis for 24 hours (per `DEFAULT_JOB_OPTIONS.removeOnFail.age`)
2. The worker's `failed` event logs the error at `error` level with full context
3. Manual intervention is expected (this is a friends-only bot — no automated alerting in V1)
4. The next scheduled repeatable job will run normally and may succeed if the underlying issue is resolved

### 8.6 Missing Reference Data

If a match-fetch job attempts to write a Match but the Sport or League record is missing (e.g., reference data sync hasn't run yet):

1. The Prisma write fails with a foreign key constraint error
2. This is not retryable — it is a dependency ordering issue
3. The job should detect this case explicitly, log it, and move on rather than failing the entire job
4. The reference data sync job (`sync-reference-data`) should be scheduled to run before the first match-fetch job

## 9. Structural Constraints and Risks

### 9.1 Traditional Match Results Cannot Be Determined From The Odds API

The Odds API's `/odds` endpoint does not return match outcomes or final scores. Traditional sport matches persist as `SCHEDULED` indefinitely from this source's perspective. Settlement of traditional sport predictions requires either:

- A manually triggered status update via Discord command
- An additional data source (e.g., API-Football, SportsDataIO) for scores

This is a known V1 limitation. The settlement sprint must address it. The ingestion architecture does not need to change — the `Match.status` and `Match.result` fields exist and are nullable precisely for this reason.

### 9.2 Esports Matches Have No Odds

As noted in section 1.6, esports matches will have no `OddsSnapshot` records. The analysis pipeline must handle this case. The `Analysis.oddsUsed` field is `Json?` (nullable), which accommodates empty odds cleanly.

### 9.3 The Odds API Teams Have No Native IDs

Slugified team names as synthetic IDs are stable within a single sport's consistent naming. If The Odds API changes a team's display name (e.g., rebranding), the next ingestion run will either update the existing Team record (same slug) or create a duplicate (different slug). This is an accepted V1 limitation.

### 9.4 The Odds API Quota Is a Hard Budget

With a limited monthly request quota, adding more sports or increasing polling frequency has a direct cost impact. The ingestion configuration must make it easy to disable individual sports from the polling list without code changes. The quota check before each API call prevents run-away consumption if the quota tracking state is stale.

### 9.5 PandaScore Opponents Array Order

PandaScore does not have a home/away concept for esports. The `opponents` array order (`[0]` = home, `[1]` = away) is a convention imposed by our mapping, not a fact from the API. This is consistent within our system but has no semantic meaning in esports context. Match prediction logic must account for this.

### 9.6 PandaScore Match IDs vs. The Odds API Event IDs

Both ID namespaces are strings in the `Match.externalId` field. The `oa:` and `ps:` prefixes enforce source traceability. Any code that extracts the original API ID from `externalId` must strip the prefix. This coupling between the ingestion layer and any consumer of `externalId` is a minor form of leaking implementation detail. In V1, it is acceptable. If it becomes a problem, a separate `sourceId` or `apiId` field could be added to the schema without breaking existing records.

## 10. Implementation Order

Implement in this sequence. Each step depends on all previous steps being complete and passing.

### Step 1 — Reference Data Sync (The Odds API)

Implement the `sync-reference-data` job processor.

**Writes:** Sport, League  
**API calls:** `getSports()` (1 call)  
**Depends on:** Nothing — this is the foundation  
**Validates:** That Sport and League upsert logic is correct before match data is attempted

### Step 2 — Traditional Match Ingestion (The Odds API)

Implement the `sync-traditional-sport` job processor.

**Writes:** Team, Match, TeamLeague (Sport and League must already exist from Step 1)  
**API calls:** `getOdds(sportKey)` (1 call per sport, no bookmakers param)  
**Depends on:** Step 1 complete (Sport and League records must exist)  
**Validates:** Team derivation logic, match upsert logic, full dependency chain

### Step 3 — Traditional Odds Ingestion (The Odds API)

Extend Step 2 to include OddsSnapshot writing, and implement the `sync-odds-for-sport` job processor.

**Writes:** OddsSnapshot  
**API calls:** `getOdds(sportKey, { eventIds, markets, regions })` (1 call per sport with filters)  
**Depends on:** Step 2 complete (Match records must exist)  
**Validates:** OddsSnapshot insert logic, `isMain` selection, inter-queue job enqueueing

At this point, the traditional sports pipeline is end-to-end: Sport → League → Team → Match → OddsSnapshot. The AI analysis pipeline can begin work on this data.

### Step 4 — Esports Match Ingestion (PandaScore)

Implement the `sync-esports-game` job processor for `getUpcomingMatches` and `getRunningMatches`.

**Writes:** Sport, League, Team, Match, TeamLeague  
**API calls:** `getUpcomingMatches(videogame)`, `getRunningMatches(videogame)` (2 calls per game, paginated)  
**Depends on:** Nothing — fully independent of Steps 1–3  
**Validates:** PandaScore entity mapping, status mapping, result mapping, pagination handling

No odds ingestion step exists for esports in V1. Step 4 completes the esports ingestion path.

### Step 5 — Scheduler Registration

Register all repeatable BullMQ jobs at application startup.

**Registers:**
- `sync-reference-data` — daily
- `sync-traditional-sport` × N sports — every 30 minutes each
- `sync-esports-game` × 3 videogames — every 30 minutes each

**Depends on:** Steps 1–4 complete (job processors must exist before registration)  
**Validates:** That the full ingestion loop runs end-to-end on a live environment
