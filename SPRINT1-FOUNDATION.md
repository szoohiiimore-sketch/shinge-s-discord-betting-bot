## 1. Repository Structure

### 1.1 Repository Type

Single repository (mono-repo within a single package). No monorepo tooling (Nx, Turborepo, Lerna). The project is a single Node.js application with a single `package.json`.

### 1.2 Branch Strategy

| Branch | Purpose |
|---|---|
| `main` | Production-ready code. Protected. No direct pushes. |
| `develop` | Integration branch for sprint work. Protected. |
| `feature/*` | Feature branches. Branch from `develop`. Merge to `develop`. |
| `fix/*` | Bug fix branches. Branch from `develop`. Merge to `develop`. |
| `release/*` | Release preparation. Branch from `develop`. Merge to `main` and `develop`. |

### 1.3 Commit Convention

Conventional Commits specification:

```
<type>(<scope>): <description>

types: feat, fix, chore, docs, refactor, test, ci
scope: module name or "infra"
```

Examples:
```
feat(matches): add match fetch service
fix(odds): handle API rate limit response
chore(infra): configure ESLint
docs(readme): add setup instructions
```

### 1.4 Gitignore

The `.gitignore` must cover:

```
node_modules/
dist/
.env
.env.local
*.log
.DS_Store
.vscode/settings.json (but keep .vscode/launch.json and .vscode/tasks.json)
```

### 2.2 Module Directory Convention

Each module in `src/modules/<module-name>/` follows this structure:

```
src/modules/<module-name>/
├── <module-name>.service.ts      # Main service class
├── <module-name>.types.ts        # Module-specific types/interfaces
├── <module-name>.errors.ts       # Module-specific error classes
└── __tests__/                    # Module-specific unit tests
    └── <module-name>.service.test.ts
```

**Exceptions:**
- `discord/` module contains `commands/` subdirectory for slash command handlers
- `scheduler/` module contains job definitions only (workers live in `src/jobs/`)
- `integrations/` is not a module — it lives at `src/integrations/` and is consumed by modules

### 2.3 File Naming Convention

| File Type | Convention | Example |
|---|---|---|
| Service files | `kebab-case.service.ts` | `match.service.ts` |
| Type files | `kebab-case.types.ts` | `match.types.ts` |
| Error files | `kebab-case.errors.ts` | `match.errors.ts` |
| Test files | `kebab-case.service.test.ts` | `match.service.test.ts` |
| Job files | `kebab-case.job.ts` | `fetch-matches.job.ts` |
| Integration clients | `kebab-case.client.ts` | `the-odds-api.client.ts` |
| Config files | `kebab-case.config.ts` | `app.config.ts` |

## 3. Package Structure

### 3.1 Package Manager

**pnpm** — strict mode enabled by default. No `package.json` hoisting.

### 3.2 Module System

**CommonJS** (`"type": "commonjs"` in `package.json`).

Rationale: Prisma Client and BullMQ have better CommonJS support. ESM interop is still inconsistent in the Node.js ecosystem for these libraries. CommonJS is the safer choice for V1.

## 4. TypeScript Configuration Strategy

### 4.1 tsconfig.json (Development)

| Setting | Value | Rationale |
|---|---|---|
| `target` | `ES2022` | Node.js 20 supports ES2022 natively |
| `module` | `commonjs` | Matches package.json type |
| `moduleResolution` | `node` | Standard for CommonJS |
| `outDir` | `dist` | Build output |
| `rootDir` | `src` | Source root |
| `strict` | `true` | Enable all strict checks |
| `esModuleInterop` | `true` | Required for CommonJS interop |
| `skipLibCheck` | `true` | Faster compilation |
| `forceConsistentCasingInFileNames` | `true` | Cross-platform safety |
| `resolveJsonModule` | `true` | Import JSON files |
| `declaration` | `true` | Generate .d.ts files |
| `declarationMap` | `true` | Source maps for declarations |
| `sourceMap` | `true` | Debugging support |
| `noUnusedLocals` | `true` | Catch dead code |
| `noUnusedParameters` | `true` | Catch dead parameters |
| `noImplicitReturns` | `true` | Ensure all paths return |
| `noFallthroughCasesInSwitch` | `true` | Prevent fallthrough bugs |
| `baseUrl` | `"."` | Path alias base |
| `paths` | `{ "@/*": ["src/*"] }` | Path alias for clean imports |

### 4.2 tsconfig.build.json (Production)

Extends `tsconfig.json` with:

| Setting | Value | Rationale |
|---|---|---|
| `exclude` | `["tests/", "scripts/", "**/*.test.ts"]` | Exclude test files from build |
| `sourceMap` | `false` | No source maps in production |

### 4.3 Path Alias Configuration

TypeScript path alias: `@/*` → `src/*`

This requires `tsconfig-paths` for runtime resolution in CommonJS.

Example import:
```typescript
import { MatchService } from '@/modules/matches/match.service';
// Instead of:
import { MatchService } from '../../modules/matches/match.service';
```

### 4.4 TypeScript Version

**TypeScript 5.5+** — Latest stable. Required for `isolatedDeclarations` support if needed later.

- No secrets in code.
- No secrets in `.env.example`.
- `.env` files are gitignored.
- Production secrets are injected via the deployment environment (Docker secrets, CI/CD variables, or platform secrets manager).

## 6. Logging Strategy

### 6.1 Logger Library

**pino** — Fast, low-overhead, structured JSON logging. Native support for log levels, child loggers, and serializers.

### 6.2 Logger Configuration

| Setting | Development | Production |
|---|---|---|
| Transport | `pino-pretty` (human-readable) | stdout (JSON) |
| Level | `debug` | `info` |
| Redact | `["DISCORD_TOKEN", "THE_ODDS_API_KEY", "PANDASCORE_API_KEY", "DEEPSEEK_API_KEY"]` | Same |

### 6.3 Log Levels

| Level | Usage |
|---|---|
| `fatal` | Application cannot continue. Exit imminent. |
| `error` | Operation failed. Needs investigation. |
| `warn` | Unexpected but non-critical. May need attention. |
| `info` | Normal operation. Key lifecycle events. |
| `debug` | Detailed information for debugging. |
| `trace` | Very detailed. Function entry/exit. |

### 6.4 Logger Module Structure

```
src/lib/logger/
├── logger.ts              # Logger factory (creates configured pino instance)
├── logger.types.ts        # Logger types (if needed beyond pino's built-in types)
└── __tests__/
    └── logger.test.ts
```

### 6.5 Logger Usage Pattern

```typescript
import { createLogger } from '@/lib/logger/logger';

const logger = createLogger('match-service');

logger.info({ matchId, sport }, 'Match fetched successfully');
logger.error({ err, matchId }, 'Failed to fetch match');
logger.debug({ oddsCount: odds.length }, 'Processing odds snapshots');
```

### 6.6 Context Enrichment

Every log entry includes:
- `timestamp` (ISO 8601)
- `level` (string)
- `name` (logger name, e.g., module name)
- `message` (string)
- `err` (error object, if applicable — automatically serialized by pino)

Additional context is added per log call via the first object argument.

### 6.7 Error Serialization

pino automatically serializes `Error` objects when passed as `err`. The serializer extracts:
- `message`
- `stack`
- `code`
- `name`

Custom error classes should extend `Error` and include a `code` property for structured error handling.

## 7. Configuration Loading Strategy

### 7.1 Config Library

**env-var** — Lightweight, type-safe environment variable parsing with runtime validation.

### 7.2 Config Module Structure

```
src/config/
├── app.config.ts           # Application-level config (port, env, log level)
├── database.config.ts      # Database connection config
├── redis.config.ts         # Redis connection config
├── discord.config.ts       # Discord bot config
├── odds-api.config.ts      # The Odds API config
├── pandascore.config.ts    # PandaScore API config
├── deepseek.config.ts      # DeepSeek API config
├── betting.config.ts       # Business logic config (bankroll, limits)
├── config.types.ts         # Config type definitions
├── config.ts               # Config loader (aggregates all configs)
└── __tests__/
    └── config.test.ts
```

### 7.3 Config Loading Flow

```
Application startup
  → config.ts loads all config modules
  → Each module reads from process.env via env-var
  → env-var validates type and presence
  → If validation fails → log error → exit with code 1
  → If validation passes → return typed config object
  → Config object is frozen (Object.freeze) to prevent runtime mutation
```

### 7.4 Config Type Definition Pattern

```typescript
// config.types.ts
export interface AppConfig {
  port: number;
  nodeEnv: 'development' | 'production' | 'test';
  logLevel: string;
}

export interface DatabaseConfig {
  url: string;
}

export interface DiscordConfig {
  token: string;
  clientId: string;
  guildId?: string;
}

// ... etc.

export interface Config {
  app: AppConfig;
  database: DatabaseConfig;
  redis: RedisConfig;
  discord: DiscordConfig;
  oddsApi: OddsApiConfig;
  pandascore: PandaScoreConfig;
  deepseek: DeepSeekConfig;
  betting: BettingConfig;
}
```

### 7.5 Config Loading Pattern

```typescript
// app.config.ts
import env from 'env-var';

export interface AppConfig {
  port: number;
  nodeEnv: string;
  logLevel: string;
}

export function loadAppConfig(): AppConfig {
  return {
    port: env.get('PORT').default('3000').asPortNumber(),
    nodeEnv: env.get('NODE_ENV').default('development').asString(),
    logLevel: env.get('LOG_LEVEL').default('info').asString(),
  };
}
```

### 7.6 Config Aggregation

```typescript
// config.ts
import { loadAppConfig } from './app.config';
import { loadDatabaseConfig } from './database.config';
// ... etc.
import type { Config } from './config.types';

let config: Config | null = null;

export function loadConfig(): Config {
  if (config) return config;

  config = Object.freeze({
    app: loadAppConfig(),
    database: loadDatabaseConfig(),
    redis: loadRedisConfig(),
    discord: loadDiscordConfig(),
    oddsApi: loadOddsApiConfig(),
    pandascore: loadPandaScoreConfig(),
    deepseek: loadDeepSeekConfig(),
    betting: loadBettingConfig(),
  });

  return config;
}
```

### 7.7 Validation Behavior

- All `Required: Yes` variables: if missing or empty, throw immediately.
- All `Required: No` variables: use default value if missing.
- Type validation: `asPortNumber()`, `asInt()`, `asString()`, etc. throw on type mismatch.
- On validation failure: log the specific variable name and expected type, then exit.

## 9. Development Workflow

### 9.1 First-Time Setup

```bash
# 1. Clone repository
git clone <repository-url>
cd betting-intelligence

# 2. Install dependencies
pnpm install

# 3. Copy environment file
cp .env.example .env
# Edit .env with your API keys and database URL

# 4. Start infrastructure services
docker compose up -d

# 5. Generate Prisma Client
pnpm db:generate

# 6. Run migrations
pnpm db:migrate

# 7. Seed reference data
pnpm db:seed

# 8. Start development server
pnpm dev
```

### 9.2 Daily Development Loop

```bash
# 1. Pull latest changes
git pull origin develop

# 2. Install any new dependencies
pnpm install

# 3. Apply any new migrations
pnpm db:migrate

# 4. Start dev server with hot reload
pnpm dev

# 5. Run tests
pnpm test

# 6. Lint and format before commit
pnpm lint:fix
pnpm format
```

### 9.3 Migration Workflow

```bash
# Create a new migration after schema changes
npx prisma migrate dev --name <descriptive-name>

# Apply migrations in production
pnpm db:migrate:prod
```

### 9.4 Testing Workflow

```bash
# Run all tests
pnpm test

# Run specific test file
pnpm test -- tests/unit/modules/matches/match.service.test.ts

# Run tests in watch mode
pnpm test:watch

# Run with coverage
pnpm test:coverage
```

### 9.5 Build Workflow

```bash
# Production build
pnpm build

# Run production build locally
NODE_ENV=production pnpm start
```

### 9.6 Pre-Commit Checklist

Before committing to `develop`:

- [ ] Code compiles without errors (`pnpm build`)
- [ ] All tests pass (`pnpm test`)
- [ ] Lint passes (`pnpm lint`)
- [ ] Format check passes (`pnpm format:check`)
- [ ] No `.env` or secrets committed
- [ ] Migration is generated if schema changed
- [ ] Commit message follows Conventional Commits

### 10.7 Health Check

A minimal HTTP server on `PORT` (default 3000) that responds to `GET /health` with `{ "status": "ok", "uptime": <seconds> }`. This is used for:

- Docker container health checks
- Deployment platform health checks
- Quick verification that the application is running

The health check server is started in `main.ts` after all services are initialized.

### 10.8 Application Lifecycle

```
main.ts
  1. Load configuration (loadConfig)
  2. Create logger
  3. Validate environment
  4. Initialize Prisma Client (connect)
  5. Initialize Redis connection
  6. Initialize BullMQ workers
  7. Initialize Discord client (login)
  8. Register slash commands
  9. Start health check server
  10. Handle SIGTERM/SIGINT (graceful shutdown)

Graceful shutdown order:
  1. Stop health check server
  2. Disconnect Discord client
  3. Close BullMQ workers (wait for current jobs)
  4. Close Redis connection
  5. Disconnect Prisma Client
  6. Exit process
```
